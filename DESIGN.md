# AgencyDesk — Design

**Tenant isolation.** Every tenant table has an `agency_id` and a `UNIQUE (agency_id, id)`. Children reference parents by the pair, not by `id` alone. For example, `tasks (agency_id, project_id) → projects (agency_id, id)`. So a Northwind task cannot point at a Pixel project even if the application code is wrong. On top of that, Postgres Row-Level Security (RLS) is enabled on every tenant table. A `RESTRICTIVE` policy requires `agency_id = app.agency_id()`. The API connects as a non-owner role (`agencydesk_api`). At the start of each request's transaction it runs `SET LOCAL` with the agency, user, role and client taken from the caller's membership row. A query that forgets `WHERE agency_id = …`, or guesses another tenant's UUID, gets zero rows. `SET LOCAL` is used so pooled connections never carry one request's context into the next.

**Blocking clients from internal content.** Tasks, comments and files each carry `visibility ∈ {internal, client}`, defaulting to `internal`. A comment or file is visible to a client only if *both* it and its parent task are `client`. Flipping a task to internal therefore hides all of its comments and files at once. This rule lives in RLS read policies, not in endpoint code, so list views, search, filters, comment threads and dashboard counts all inherit it. Clients have no insert/update policy on `tasks`, so they cannot create tasks or change status. They can insert only `client` comments on tasks they can see. A trigger lets them change only the approval fields on a client-visible file. Raw time entries are staff-only, because their notes are internal. Clients get hour totals through `app.project_hours()`, which counts client-visible tasks only.

**One person, two agencies.** `users` holds one row per human (unique email, one password). `agency_memberships (agency_id, user_id, role, client_id)` holds that person's role in each agency. A `CHECK` requires `client_id` exactly when the role is `client_user`. Login checks the password once and then lists the person's active memberships. The user picks one, and the session token is scoped to that membership. Every request re-reads the membership, so removing someone takes effect immediately. Switching agencies issues a new token; a request never carries two tenants.

**Edge case I'm proud of: removing a member mid-task.** `tasks (agency_id, project_id, assignee_user_id)` is a foreign key to `project_members`, with `ON DELETE SET NULL (assignee_user_id)`. The database therefore guarantees that the assignee is always a current member of that project. Deleting a `project_members` row automatically unassigns only that person's tasks, leaving status, history and time entries untouched. A trigger logs each change as `auto_unassigned_member_removed`, with the admin as the actor. No application code path can leave a task assigned to someone who has lost access.

**Invite races.** A partial unique index `(agency_id, email) WHERE status='pending'` means a resend is an `INSERT … ON CONFLICT DO UPDATE` that replaces the token hash on the same row. The old link stops working. `app.accept_invite` locks the invite with `SELECT … FOR UPDATE WHERE status='pending'`, so a concurrent second accept waits and then finds nothing. `users.email UNIQUE` + `ON CONFLICT` reuses an existing person instead of creating a second account.

All of the above is proven in `tests/test_db_rules.py`, which runs against the real `agencydesk_api` role.
